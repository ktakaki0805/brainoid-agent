## 2. 目指す利用体験

スマホで「寝る前はリビングの照明を暖色にしたい」と明示的に記憶させる。共有してよい記憶として保存した場合、ディスプレイで「寝る準備をして」と依頼すると、その世帯の許可済み照明へ設定を送る。スマホで記憶を訂正・削除すると、ディスプレイでの次の判断にも反映される。

同じエージェントであることは、全員がすべての会話を読めることを意味しません。個人の会話・記憶・カレンダーは所有者の権限に従い、共有ディスプレイで表示・発話するには別途条件を満たす必要があります。

## 3. MVPに含む機能

- ユーザー認証、世帯・ワークスペース単位のテナント、会員管理、端末のペアリングと失効。
- 共通の人格設定、テキスト会話、タップで開始する音声会話、2Dキャラクターの状態表示。
- 出典を持つグラフ型記憶の保存・検索・訂正・削除。
- ノート、タスク、リマインダー、スマホとディスプレイへの通知。
- Google Calendarの参照と、本人による具体的な内容の確認後の作成・変更・削除。
- Home Assistantに登録された照明・空調のうち、許可リストにある機器の限定操作。
- 個人用セッション、通信切断からの回復、記憶・アカウントの削除、運用監視と利用量の制御。

MVPはオンラインで動作します。常時ウェイクワード、声紋による本人認証、ローカルLLM、推測した記憶の自動確定、解錠・決済などの高影響操作は初版の対象外です。将来のローカル実行に必要なModelProvider・MemoryStore・ToolExecutor等の境界は設計します。

## 4. 採用する構成

| 領域 | 初期設計 |
| --- | --- |
| 共通UI | React、TypeScript、Vite |
| スマホ | Capacitor。Android・iOSのネイティブ機能はアダプターで接続 |
| スマートディスプレイ | Raspberry Pi OS 64-bit、Chromium kiosk、Python端末サービス、systemd、SQLite |
| APIとエージェント | Python、FastAPI、Pydantic、共通AgentCore |
| AI・音声 | Google Gen AI SDK、Google CloudのGemini、Speech-to-Text、Text-to-Speech |
| データ | Firestore Standard。グラフはentitiesとfactsで表現し、必要な範囲を検索 |
| 実行基盤 | Cloud RunのAPIとworker、Cloud Tasks、Cloud Scheduler |
| 認証と通知 | Firebase Authentication、端末専用資格情報、FCMとiOS APNs連携 |
| 外部連携 | Google Calendar、LAN内のHome Assistant |
| 機密情報・保管 | Secret Manager、Cloud Storageの制御・リリース用bucket |
| 構築・配布 | Terraform、Docker、GitHub Actions |

専用グラフDBは初版では採用せず、関係探索の量・読取コスト・実装複雑度を測って再評価します。モデルID、音声、リージョン、最低対応OS、各ツールのバージョンは実装の初期検証で固定します。

## 6. このパッケージの確認方法

ZIPを展開したディレクトリで、次のコマンドを実行できます。

~~~bash
python3 -m pip install -r scripts/requirements-docs.txt
python3 scripts/validate_docs.py
~~~

検証スクリプトは相対リンク、文書の必須ファイル、実装チケットのID・依存関係・要件対応、OpenAPIの構造・参照、JSONの構文・参照などを点検します。アプリの起動、GCPへのデプロイ、実機性能、製品のセキュリティ適合を検証するものではありません。

アプリを動かすためのセットアップは、[開発ガイド](docs/05-development-and-testing.md)にある初回実装タスクを完了した後に有効になります。存在しないリポジトリURLや起動コマンドをクイックスタートとして案内しない方針です。

## 8. チームでの最初の進め方

1. 01のMVPと受入基準をレビューし、必要な変更を要件ID単位で記録する。
2. 02でAPI・スマホ・Pi・データ・運用の担当境界を決め、03と04を共通の契約としてレビューする。
3. 05の初回実装タスクから、テナント分離されたテキスト会話までの縦の動作を作る。
4. 明示記憶、ノート・タスク、カレンダー、家電操作、音声の順に受入シナリオを増やす。
5. 06の復旧・削除・公開確認を実施し、測定結果をもとに設計目標と対応環境を確定する。

設計変更は実装と同じPRで更新します。採用理由は02の設計判断、受入条件は01、具体的な検証方法は05に記録し、同じ内容を別文書へ重複して書きません。

具体的な実装の着手順序とPRの境界は[実装チケット](docs/08-implementation-tickets.md)を参照してください。チケットIDは文書内の識別子であり、GitHub等のIssueを作成済みという意味ではありません。
