# 全実装チケットを完了まで進める

[implement-ticket](../implement-ticket/SKILL.md) を1件ずつ実行し、記録まで完了したら台帳から次の対象を選び直す。会話の圧縮は環境の自動圧縮に任せ、各回の手動操作や続行確認を挟まず、全件が `done` になるまで続ける。

このSkillは反復と進捗の引継ぎを管理する。チケットの選択、実装担当と独立レビュー担当への委譲、検証、修正、`main` へのConventional Commits、台帳・ログ更新は `implement-ticket` を正本とし、省略しない。同Skill末尾の「次のチケットには進まない」は内側の1回に適用し、その完了後の継続はこのSkillが担当する。各回の報告は進捗として伝え、全体が完了するまで通常の最終報告で終了しない。

## 開始・再開

1. リポジトリルートと適用される作業規約を確認し、このSkillと `implement-ticket` を読む。既存変更を把握し、同じworktreeで複数のチケットを並行実装しない。
2. `docs/08-implementation-tickets.md` を仕様・依存の正本、`docs/implementation-status.json` を実装状況、`docs/implementation-log.md` を検証・レビュー・コミット証跡として読む。文書の古いチェック欄や会話だけで完了を判断しない。
3. 下記のローカル再開状態があれば、リポジトリ・履歴・台帳と照合する。`running_ticket` のまま実装コミットだけが存在する場合は、`implement-ticket` の記録復旧手順を優先する。両コミットまで済んでいれば完了条件を確認して `ready` にし、同じチケットを再実装しない。

## 1件ずつ反復する

リポジトリルートで既存の読み取り専用スクリプトを使う。

```bash
python3 .agents/skills/implement-ticket/scripts/ticket_plan.py check
python3 .agents/skills/implement-ticket/scripts/ticket_plan.py next
```

1. `check` が成功したら、`next` のJSONと終了コードを確認する。IDを指定せず、既存の依存順と文書中の順序をそのまま使う。件数は固定しない。
2. `next` が終了コード `4` かつ `result: "all_done"` なら全体完了の確認へ進む。`2` は不整合、`3` は未完了の依存として原因を扱い、全件完了と混同しない。`blocked` は飛ばさず、解消条件を確認する。
3. 選択したチケットIDと開始時の `HEAD` を再開状態に保存して `running_ticket` にする。そのIDを対象に `implement-ticket` の全工程を1回実行する。別コンテキストの実装担当と、各ラウンドで新規の独立レビュー担当を使う。同Skillに従いローカルの `main` に実装コミットと記録コミットを作成する。
4. 対象が `done`、必須検証が成功、独立レビューが `approve`、未解決の要修正指摘がゼロ、両コミットが現在の履歴に存在し、今回の記録が未コミットで残っていないことを確認する。`ticket_plan.py check` を再実行し、失敗時は次へ進まない。
5. 完了ID、両コミット、検証結果、レビュー回数、完了数／全件数を短く伝える。再開状態を `ready` として保存し、次の対象を選ぶ。
6. 未完了の対象があれば、そのまま次の回を実行する。圧縮の発生・完了確認や、ユーザーの手動操作・続行指示を待たない。

## ローカル再開状態

会話圧縮や中断をまたぐ補助情報は、`git rev-parse --git-path implement-all-tickets-state.json` が返すパスにJSONで保存する。ファイルはGit管理対象に追加せず、台帳の代替にも使わない。

以下を開始時、工程の切替時、チケット完了時、中断時に更新する。

- `skill`: `implement-all-tickets`、`repository`: リポジトリの絶対パス。
- `phase`: `ready` / `running_ticket` / `blocked` / `complete`。
- `ticket`: 今回の対象ID（未選択なら `null`）、`base_commit`: 開始時のHEAD。
- `implementation_commit`、`record_commit`、`log_anchor`: 確認済みの値。未確定なら `null`。
- `next_action`: 実装、レビュー、記録復旧、次の選択などの再開工程、`blocker`: 中断理由・再開条件（なければ `null`）。
- `updated_at`: タイムゾーン付き日時。

新しいチケット開始時は前回のコミット情報を対象のものとして流用しない。台帳の `done` と実装・記録コミットを確認してから次の選択へ進む。

## 自動圧縮をまたいだ継続

1. `/compact` の明示実行やユーザーへの手動実行依頼は行わない。圧縮のタイミングは環境に任せ、圧縮機能の確認や完了通知を次のチケットの開始条件にしない。
2. 自動圧縮はチケットの途中でも起こり得るため、検証・レビュー結果は `implement-ticket` の手順どおり、その都度ログへ保存する。引継ぎには全件完了まで継続する目的、現在の対象と工程、担当エージェントの識別子、確認済みのコミット、再開状態とログのパスを残す。
3. 圧縮後はこのSkillと必要な `implement-ticket` の手順を再確認し、保存状態・台帳・ログ・Git履歴から未完了の工程を続ける。進行中の担当エージェントがいれば状態を確認して引き継ぎ、同じ実装やレビューを重複起動しない。圧縮だけを理由にターンを終了したり、ユーザーへ再開指示を求めたりしない。

## 中断・全体完了

`implement-ticket` が解決できない外部前提・権限・仕様判断・検証失敗で中断した場合、その手順で台帳とログに理由・再開条件を残し、ループも中断する。同じ失敗を進展なく繰り返さず、未完了の対象を飛ばさない。ユーザーの停止指示も尊重する。長時間かかることや1件完了したことだけでは終了しない。

全体完了は、`check` 成功、全件 `done`、ID指定なしの `next` が `all_done`、実装・記録の未完了なしを条件とする。開始時点ですでに全件完了していれば新たな実装は不要。再開状態を `complete` にして、今回完了したID、総完了数、検証結果、台帳・ログの場所を報告する。全体完了前の中断は完了と表現せず、停止箇所と再開手順を示す。

このSkillの実行に含まれるのは既存Skillによるローカル作業とコミットであり、push、PR作成・merge、実環境の変更は別途依頼された場合に限る。
