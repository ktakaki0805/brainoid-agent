# 実装チケットを1件完了する

1回の呼出しで扱うのは1チケット。ID省略時は依存グラフのトポロジカル順で次の1件を選ぶ。実装、独立レビュー、修正、ローカルの `main` へのコミット、作業ログの記録まで進める。

## 正本と準備

リポジトリルートで作業し、適用される `AGENTS.md`、`CONTRIBUTING.md`、`docs/05-development-and-testing.md` の完了条件を確認する。

- 仕様・依存関係: `docs/08-implementation-tickets.md` の詳細節（「依存PR」が正本）。
- 実装状況: `docs/implementation-status.json`。
- 検証・レビュー・コミットの証跡: `docs/implementation-log.md`。更新前に同ファイルの記録規約を読む。
- チケットの関連要件・設計・schemaは対象部分を読む。未確定の外部設定を推測で確定しない。

`git status --short`、現在のブランチ、`HEAD`、staged/unstaged差分を確認する。実装とコミットは `main` で行い、このSkill用の作業ブランチを作らない。別ブランチにいる場合は既存変更・未取り込みコミットを確認し、無関係な変更を持ち込まずに `git switch main` で切り替える。`main` が別worktreeで使用中なら、そのworktreeの状態を確認してそこで作業する。切り替えや変更の分離が安全にできない場合は、原因と再開条件を報告する。既存変更を消去・stash・勝手にmergeして解決しない。開始時の `main` のbase commitと既存変更を控える。

前回の実装コミット後に台帳・ログの記録だけが中断している場合は、その記録を先に完了する。保存済みの検証・レビュー証跡と実装コミットの内容が一致するか確認する。証跡が不足していれば必要な検証と新しい独立レビューを行い、過去の承認や回数を推測で補わない。追加修正がなければ新しい実装コミットを重ねない。

## チケットの選択

同梱の読み取り専用スクリプトを使う。次の例はリポジトリルートから実行する。

```bash
# ID省略時
python3 .agents/skills/implement-ticket/scripts/ticket_plan.py next
# ID指定時
python3 .agents/skills/implement-ticket/scripts/ticket_plan.py next --ticket BA-FND-01
# 全体の順序・台帳の整合を確認
python3 .agents/skills/implement-ticket/scripts/ticket_plan.py order
python3 .agents/skills/implement-ticket/scripts/ticket_plan.py check
```

スクリプトは各詳細節から依存を抽出し、Kahn法でソートする。同時に選べる頂点の優先順位は**文書中の詳細節の登場順**とする。段階、優先度、IDの辞書順で依存順を上書きしない。

- ID省略時: ソート順で最初の `done` 以外を選ぶ。途中の `in_progress` / `in_review` は証跡を確認して再開する。
- ID指定時: その1件だけを対象とする。未完了の依存先を一覧で報告し、勝手に依存先へ対象を変更しない。
- `blocked` を自動的に飛ばさない。原因が解消済みならその1件を再開し、解消していなければ原因・再開条件を報告する。
- `done` の指定、全件完了、存在しないID、循環、未定義の依存、壊れた台帳では実装を始めない。
- `done` は受入条件と独立レビューを満たす実装コミットが現在の履歴にある状態。PR mergeや実環境への配備を意味しない。依存先のコードが現在の作業環境にあることも確認する。

スクリプトの終了コードは `0`: 検証成功／選択可能、`2`: 入力・台帳不整合、`3`: 未完了の依存、`4`: 対象なし。`blocked` の出力は原因を確認するための選択結果であり、自動再開の許可ではない。

対象の目的、成果物、受入条件、検証方法、対象外、外部前提を読み、今回の範囲と選択理由を短く伝える。受入条件を検証項目に対応させる。外部前提が必須なら実装可能部分と区別し、チケットが認めるfake/emulatorによる完了範囲を確認する。

作業ログに今回の記録見出しを用意し、台帳の `log_anchor` に結び付ける。検証終了時・各レビュー終了時に、コマンドと結果、担当識別子、指摘・対応・判定・確認済みの回数をその都度ディスクへ保存する。レビュー対象のbase commit、ファイル一覧と内容のSHA-256（削除も明記）も残す。最終コミット前は未コミットの下書きでよい。会話履歴だけを再開の根拠にしない。

## 実装担当とレビュー担当を分ける

親エージェントは選択・引継ぎ・進捗・コミット・ログを担当し、実装や修正は実装担当へ渡す。委譲時に [担当別の依頼文](references/agent-prompts.md) を使う。

- 実装担当を独立した子エージェントとして起動する。`collaboration.spawn_agent` が使える環境では `fork_turns: "none"` とし、作業パス、チケット、仕様、制約、検証項目を明示する。
- レビュー担当は**実装担当とは別のエージェントを毎ラウンド新規起動**する。同じく `fork_turns: "none"` を使い、実装担当の会話・内部推論・自己評価を継承しない。差分、仕様、受入条件、検証の事実を渡す。
- 修正は元の実装担当へ指摘と必要な検証を返す。実装担当を再起動する場合もレビュー担当を兼任させない。
- 同一worktreeでは書き手は実装担当1名だけ。レビュー中は実装の変更を止め、レビュー担当は製品コード・index・台帳を変更しない。
- 独立したエージェントを起動できなければ、その制約を報告して `blocked` を記録する。単一コンテキスト内の役割演技を独立レビューと扱わない。

実装担当へ渡す前に、対象だけを `in_progress` にして `branch: "main"`、`base_commit`、`updated_at` を記録する。ユーザーが依頼したこのフローの `main` へのローカルコミットは実行範囲に含む。push、PR作成・merge、実環境の変更は別途依頼されている場合だけ行う。

## 実装 → レビュー → 修正

1. 実装担当が受入条件に必要なコード・テスト・契約・文書を変更し、対象に応じた検証を行う。まだ存在しないCIやコマンドを実行済みとしない。
2. 親は変更ファイルと検証結果を受け取り `in_review` にする。レビュー対象には未追跡ファイルと関連文書も含め、既存の無関係な差分を除く。base commit、対象パス、差分と新規ファイルの内容を特定できる状態で渡す。
3. レビュー担当は受入条件、依存先との整合、正例・負例、回帰、変更が触れる認可・削除・外部副作用を確認する。指摘には場所、問題、影響、必要な修正または検証を付ける。
4. `request_changes` なら `in_progress` に戻し、指摘を実装担当へ返す。実装担当は対応・根拠・再検証結果を返す。根拠のある反論も次のレビューで確認する。
5. 新しいレビュー担当が**最新の差分全体**と前回指摘への対応を確認する。修正箇所だけの確認で終了しない。
6. `approve`、受入条件を裏付ける検証、未解決の要修正指摘ゼロが揃うまで繰り返す。任意の改善提案は未対応理由をログに残せる。レビュー後に製品コード・テスト・契約が変わったら再レビューする。

検証の失敗、外部前提、権限不足、仕様判断の不足を成功扱いにしない。同じ指摘で2回続けて新しい根拠も修正の進展も得られない場合は、無限反復せず `blocked` にして判断事項と再開条件を記録する。単に作業が長いことは中断理由にしない。

## コミットして記録する

実装と記録は同じチケットの2コミットにし、どちらも `main` に直接コミットする。中断理由だけの記録コミットも同じ扱いとする。各コミット直前に `git branch --show-current` が `main` であることを確認する。違っていればコミットせず、準備手順に戻って状態を確認する。実装コミットの実際のハッシュを後続のログに残し、自己参照やamendによるハッシュ変更を避ける。

1. 最新差分がレビュー対象と一致すること、必要な検証が成功したことを確認する。台帳・作業ログを除く対象ファイルを明示してstageし、`git diff --cached` と `git diff --cached --check` で無関係な変更が入っていないことを確認する。既存staged変更を一緒にcommitしない。
2. 実装・テスト・関連文書を Conventional Commits でcommitする。形式は `type(scope): BA-XXX-NN 変更内容`。種類は実態に合わせて `feat`、`fix`、`build`、`chore`、`test`、`docs`、`refactor` 等を選ぶ。例: `build(workspace): BA-FND-01 pin toolchains and dependencies`。
3. commit成功後、`git rev-parse HEAD` とcommit内容を確認する。hook等がレビュー対象を変更したら、追加の修正・再検証・再レビューを経てから完了にする。失敗時に `done` を付けない。
4. `docs/implementation-log.md` の保存済みの途中経過に、完了結果と実装コミットの完全なハッシュを追記して今回の記録を仕上げる。受入条件と検証結果、各レビューラウンドの指摘・修正・再確認、未実施の理由が揃っていることを確認する。
5. `docs/implementation-status.json` の対象を `done` にし、`implementation_commit`、`log_anchor`、`updated_at`、`review_rounds` を記録する。既存チケットの記録を初期化しない。
6. `ticket_plan.py check`、`python3 scripts/validate_docs.py`、記録差分の確認を行い、台帳とログだけを `docs(tickets): record BA-XXX-NN completion` でcommitする。記録コミットのハッシュは最終報告に示し、同じログへの自己参照更新を繰り返さない。
7. `git status --short` と両コミットの内容を確認する。元からある変更を除き、今回の作業が未記録で残っていないことを確かめる。

実装commit済みで記録commitに失敗したら、実装ハッシュと記録待ちのファイルを報告し、次回は記録工程から再開する。未完成で停止する場合も台帳・ログに理由と検証の現状を残す。可能なら記録だけを `docs(tickets): record BA-XXX-NN blocker` でcommitし、未承認の実装を混ぜない。

最終報告にはチケットID、変更内容、検証結果、レビュー回数、実装と記録のコミット、台帳・ログの場所を簡潔に示す。必須条件が残るときは完了と表現しない。次のチケットには進まない。
